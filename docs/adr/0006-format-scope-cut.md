# ADR-0006 · 格式范围收敛：不做 `.aab` / `.ipa` / `.appx` / `.msix`

- 状态：**已采纳**（范围裁剪，M4 收敛）
- 日期：2026-11-04
- 相关：[design.md §7](../design.md)、[formats.md §3/§4/§6](../formats.md)、[roadmap.md M4](../roadmap.md)、[verification.md R-0011/R-0012/R-0013](../verification.md)

## 背景

M0 的格式矩阵列了七类安装包（APK 家族、AAB、IPA、HAP、APPX/MSIX），M4 原计划逐个补齐。
M4a（`.xapk/.apks/.apkm`）与 M4d（`.hap`）交付后，用户 2026-11-04 明确：

- `.ipa` 属苹果生态，做这类文件的人必然在 macOS 或用助手类工具，不在本扩展的目标场景；
- `.appx/.msix` "应不在计划功能内"（`design.md §7` 当初就把它写成"用户场景少"的待议项）；
- `.aab` 目前不常见，等真有需求再说。

补充事实（2026-11-04 调研，用于记录判断依据，不是猜测）：

| 格式 | 现状 |
| --- | --- |
| `.aab` | Google Play 自 2021-08 起要求新应用用 AAB 发布，2023-06-30 起电视应用更新也必须是 AAB；**AAB 是发布格式、不能直接安装**，设备侧由 Play 下发 split APK，第三方分发用的是 `.xapk/.apkm/.apks`（APKMirror 2020 起支持 split APK）。磁盘上出现 `.aab` 的场景基本只有开发者本地构建产物 |
| `.ipa` | Apple 生态；Windows 上只出现在越狱/助手工具的工作目录 |
| `.appx/.msix` | 已安装的商店应用图标由系统提供；独立的 `.msix` 文件在普通用户目录罕见 |

## 决策

1. **v1 支持的扩展名固定为五个**：`.apk .xapk .apks .apkm .hap`（注册表、缩略图、属性页一致）。
2. `.aab` **不做**；只有出现"本机确实有 `.aab` 要看图标"的实际需求时，才新开 ADR 并单独排期。
3. `.ipa`、`.appx`、`.msix` **不做**，也不再保留其静态图标设计（M5 的"每格式一枚 ico"从 5 枚降为 3 枚：APK / XAPK / HAP）。
4. `formats.md` 里这三类格式的**结构知识保留**（以后真要做时不用重新调研），但每节必须标明"不实现（ADR-0006）"。
5. M4 的验收范围随之收敛为 M4a + M4d，两者均已交付（R-0011、R-0012/R-0013）。

## 后果

**正面**

- 剩余工作量从"M4b/M4c/M4e 共 4.5–5.5 人日"直接归零，M4 收敛完成，项目进入 M5。
- 不再需要为三种格式准备样本与测试固件，`formats.md §8` 的限额也不必再为 AAB 的 protobuf 扩张。
- 用户界面承诺与实现一致：注册表里只有真能解析的扩展名。

**负面 / 需要记住的**

- 若将来要支持 AAB，成本仍是剩余格式里最高的（protobuf manifest + `resources.pb`，2–3 人日），且必须新开 ADR。
- 小图标 / 列表视图只做 3 枚静态 ico；拿到 `.aab`/`.ipa`/`.appx` 文件时它们保持系统默认图标。

## 替代方案与被否原因

| 方案 | 否决原因 |
| --- | --- |
| 继续按 M4 原计划补 AAB | 收益是"开发者构建产物能看图标"，但样本与真实需求都不存在；成本 2–3 天且是剩余格式里最贵的 |
| 只做 AAB 的"轻量版"（读 `BundleConfig.pb` 显示包名、不出图标） | 图标是缩略图扩展的核心价值，半成品会误导用户 |
| APPX 顺手做（原估 0.5 天） | 用户明确说不在计划内；且商店包已安装后系统自己会显示图标 |

## 修订条件

- 出现真实的 `.aab` / `.ipa` / `.appx` 使用场景（用户提供样本并说明用途）→ 新开 ADR，编号递增；本 ADR 不改结论。
- 若要恢复静态图标，仅需注册表 + 图标资源，不动解析代码路径（不违反 ADR-0001/0002）。
